The initial baseline was **241 fast cases PASS** before edits. An 882-file SHA-256 baseline and the existing dirty diff were preserved locally. The original October 6 audit and earlier slice evidence remain unchanged. Native regression tests now reproduce denied/missing DDL using both actual restricted database permissions and injected statements; they assert the previous marker remains pending before retry. DDL success notifications alone do not establish physical success.

`IDLM_DB::create_tables()` retains ownership of the core declarations through `schema_statements()`; `IDLM_Schema_Migration` coordinates verification and marker publication for core/routing installers. Installer entry points retain their names and return `true` or `WP_Error`; bootstrap names remain stable. Verification checks every required core column's type/width/signedness, nullability, explicit default and auto-increment requirement; primary/unique/ordinary indexes must have the expected ordered columns, uniqueness and full lengths. Integer display widths are normalized for MySQL versions that omit them. Required tables use InnoDB. Extra historical columns/indexes are retained, and no table/column is dropped by the installer.

New core and routing tables explicitly declare InnoDB. Existing nontransactional tables are **not automatically converted**: the installer returns an actionable backup/operator-migration error and leaves the completion marker pending. The existing private-file installer must also return verified success before the core marker advances. Quotation DDL, historical quotation migration and quote transaction health remain separate QUO-004/005/007/010 work; this slice does not close those findings.

One database/prefix-scoped MySQL session lock serializes core, routing and backfill work. Installers take the lock before reading durable markers; nested core installation shares it. Markers are reread from the options table rather than relying on a stale request cache, and publication checks lock ownership and reads the stored value back after `update_option`. A failed marker write is an error, including when physical DDL already succeeded. `finally` releases the lock; a terminated process loses its session lock. The native interrupted worker exits after real DDL, before verification/publication, and the next process completes safely. The synchronized two-process race exercises separate connections, with one completing and the other returning a retryable busy result.

DDL is not placed inside a pretend rollback transaction. Partial successful DDL remains durable; subsequent runs reconcile/verify it. Qualification/Won clock updates are checked before core completion; reporting-start time is written only after verified physical installation and successful clock updates, and existing reporting time is retained. Older release-version markers are no longer adopted as physical-schema evidence; newer core/routing markers refuse incompatible downgrade work.

All seven core backfill completion markers advance to `1.0.1` only after checked success, rechecking earlier `1.0.0` markers that could hide failures. Handoff treats an actual empty pre-sales population as complete and detects read/write errors. Workflow checks each required SQL write, including the final orphan-task delete. Assignment/conversion repair, duplicate-quality repair and both task-cleanup writes detect SQL failures; zero affected rows are successful no-ops. Partial idempotent data repairs can remain durable after failure; no aggregate rollback is claimed for these legacy repair steps. CORE-004/005 aggregate atomicity remains open. Manual task cleanup now reports failure when its checked helper fails.

Legacy duplicate attribution processes at most 100 duplicate rows per invocation. A durable last-ID checkpoint advances only after the batch succeeds. An interrupted batch checks existing `(legacy_duplicate, legacy-duplicate-ID)` identities and their canonical lead before skipping an already persisted row; existing payload/timestamps are retained. Insert/read/checkpoint failures and zero inserted rows retain the completion marker, and a full batch returns a progress/retry error until a later request verifies exhaustion. Other existing set-based repair statements remain unbounded; workload/time-budget qualification belongs to CORE-012/T21 and is not claimed here.

Completed markers use a fast path without DDL or migration-lock contention on ordinary requests. Physical verification is performed during installation/versioned migration; this is not a continuous detector of arbitrary external schema drift. Activation stops before scheduling/activation success when core or routing migration fails. Runtime stops before CRM/integration/provider/quotation initialization. IDLM AJAX/REST requests receive a generic retryable 503 without PII or internal table names; administrators receive an escaped notice identifying required operator repair. The WP-Cron bootstrap branch also stops on incomplete migration; actual cron dequeue/recovery was not separately exercised. Login requests retain their scoped-runtime skip.

The complete backup manifest accepts current core `1.3.6` and earlier `1.3.5` only when its complete physical column manifest, quotation version and aggregate validation still match. Older/unknown manifests remain rejected. Checked backfill markers, reporting-start time and the new cursor are excluded from backup import/export. The narrow `1.3.5` adapter tolerates its formerly exported backfill/reporting marker rows but ignores them during restore; current manifests attempting to import those protected markers are rejected. Legacy complete v1 backups without manifests retain their existing validation/ignore policy.
