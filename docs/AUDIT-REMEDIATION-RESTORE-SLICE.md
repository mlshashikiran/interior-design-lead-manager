The pre-fix multipart HTTP characterization reproduced the finding: an empty table/settings payload returned success and changed persistent CRM state. The other 245 HTTP/stdio cases and all 241 fast / 31 native baseline cases passed. The fixture repaired its own data after this characterization. A 699-file hash/source/dirty baseline was captured before this slice; original audit and earlier remediation evidence are preserved.

The existing administrator-only export/restore callbacks, JSON format/version 1, multipart field names, nonce actions, return redirects and settings markup remain stable. Export now reads all 21 tables, eligible settings and assigned-user identities in one repeatable-read snapshot. Missing tables/columns/required unique indexes, non-InnoDB tables/options/users, or any read failure produce an error rather than a partial download. An optional schema/user manifest describes the current columns and existing assigned-user IDs/logins. Empty mandatory tables remain explicit.

Restore requires a complete same-site aggregate. It validates exact column sets, canonical integer/decimal bounds, UTF-8 and field lengths, real dates/nullability, unique IDs, lead/quote/revision/section relationships, revision ancestry, duplicate-lead cycles, existing assigned users and safe serialized settings. Database-valid controls in historical text remain lossless. Historical catalogue IDs and identity-review candidate IDs remain hints, because catalogue/deletion history can remove their targets. Temporary tables copied from the live schema enforce actual collation and unique constraints before persistent deletion; uploaded rows are suppressed from native database-error logs. The checked transaction includes settings and a protected recovery generation; injected late table/settings/commit failures roll everything back without cancelling queues. Modern WordPress autoload values and individual option caches are preserved correctly.

Current API credentials, schema/access/migration markers and runtime counters are excluded and never imported. Successful recovery clears queued outbound intents and database autosaves, rotates read caches and does not immediately prune restored historical diagnostics. Autosaves carry a generation, so cached pre-recovery working copies cannot be displayed after recovery. Existing quotation sequence pairs retain the maximum of live and imported counters, including live pairs absent from an older backup. IDs are restored with DELETE/INSERT rather than resetting AUTO_INCREMENT.

Complete legacy v1 backups without the added manifest have a narrow adapter: same site URL, all current tables/columns/types/relationships and existing assigned-user IDs are required; protected/runtime settings are ignored. No omitted-table defaults, schema guessing or cross-site/user remapping is performed. Backups containing invalid/orphan historical data need operator reconciliation before restore; export can still preserve that evidence. Private files, WordPress attachments/users and credentials remain outside JSON recovery; current managed private-file records block this partial restore. Use full WordPress database recovery for those records, plus filesystem recovery for legacy/media files still stored on disk.

A database-scoped coordinator and session-held worker slots fence bootstrap, IDLM HTTP mutations and affected CAPI/Interakt/batch/audience, assignment/task, retention/telemetry and private-maintenance workers. Restore and CRM reset refuse active work and retain their gate through commit, queue cancellation and cache cleanup. New internal CAPI/Interakt queued argument lists append an optional generation; their existing public callback names and preceding arguments remain compatible. Historical queued callbacks execute only at generation zero. Stale generations stop before logs, retries or HTTP. Busy current-generation queued work defers briefly. Provider sends recheck the lease immediately before and after transport; a lost lease prevents result logs/retries. An already-started provider request cannot be recalled. Normal successful owner/explicit manager workflows remain covered by the accumulated HTTP tests. Reset advances the generation but its separate review-PII omission (CORE-008) is deferred.

Session locks require one MySQL primary and support for multiple named locks per connection; unavailable locks fail closed. The implementation follows the [MySQL session lock contract](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html). It is cooperative fencing for the covered plugin paths, not a distributed database/outbox protocol. Third-party direct SQL, external backups, process suspension/disconnect across arbitrary non-provider writes, failover and multi-primary topology remain outside the demonstrated guarantee. Avoid concurrent external schema/DDL changes during recovery.
