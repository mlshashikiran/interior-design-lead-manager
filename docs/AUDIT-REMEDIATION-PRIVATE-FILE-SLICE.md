## Legacy migration and lifecycle

Hourly `idlm_private_file_maintenance` scans ten leads and cleans ten journal entries per run, cycling a saved cursor; the first run is scheduled five minutes after boot. `wp idlm integrity files` invokes the same bounded operation and reports aggregate scanned/failed/pending counts. It copies and verifies local WordPress main files, original images, generated sizes and backup sizes before replacing saved URLs and removing public paths. Lead rows are locked; cleanup locks/reloads each journal row to serialize overlapping attempts. Partial unlink, failed commit and interrupted cleanup remain retryable. The journal and verified protected chunks survive filesystem operations, which cannot be rolled back by MySQL.

Lead-tagged uploads that were never saved also migrate, without adding them to the saved form. Newly uploaded and migrated unsaved files remain available for seven days, then are revoked and queued for erasure. Saving a valid pointer makes a file active. Removing a saved pointer immediately denies its download; cleanup deletes the bytes and WordPress attachment. Lead deletion/reset revoke and remove private chunks within their owning transaction, then perform filesystem/attachment cleanup after commit. Legacy tagged unsaved files are included in deletion. A failed lead deletion rolls file state back. Cleanup batches larger than the immediate limit resume through maintenance.

Migration refuses remote/unmanaged URLs, shared or foreign-owned attachments, missing sources, unsafe/symlink/traversal paths, unsupported content and oversized archives. Such records/source files are retained for operator resolution instead of claiming success or removing unverified originals. An unresolved public source remains a disclosure risk until resolved; failed/pending counts require attention. The production database and old URLs have **not** been migrated by this local work.

Before production migration: take a full WordPress database and existing uploads backup; rehearse on a disposable copy; repeat bounded runs until failure/pending counts are resolved; directly request each old main/variant URL without cookies; check authorized new downloads and ownership/capability revocation. Purge any existing CDN/server caches separately. This code cannot erase copies already cached or downloaded elsewhere. New database-only file bytes require no web-server deny rules; legacy-copy revocation still depends on successful unlink and upstream cache handling.

The plugin JSON backup explicitly excludes private bytes and WordPress attachment/user identities. It declares this policy in the payload and Backup & restore view. Partial JSON restore is rejected before destructive work when private records exist, storage verification fails after installation, or the incoming lead payload contains private download pointers. Recovery of these files requires a consistent full WordPress database backup/restore (plus existing uploads for unmigrated media). Ordinary deactivation clears the maintenance schedule and preserves data. Full restore integrity, worker fences and numbering continuity remain INT-003/M2 work.
