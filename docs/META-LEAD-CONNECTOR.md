# Direct Meta leads and Interakt intake

Builder: Shashi. Local unreleased iteration, 2026-10-17. Core schema remains 1.3.9; release version is unchanged. No production connection is enabled by this change.

## Recommended setup for separate customer installations

The publisher deploys one shared [Facebook Connect service](../services/facebook-connect/README.md) and provisions a separate installation credential in each customer's protected `wp-config.php`. Meta app credentials and Page access tokens remain on the publisher service. This is a local implementation; hosting and Meta approval are still required before customer use.

Customers open **Settings → Lead capture**, click **Connect Facebook**, approve permissions, select their Page and individual active forms, then click **Start syncing selected forms**. The service confirms lead access and subscribes the Page before activating sync. Change Page/forms starts fresh consent; disconnect stops local sync and removes the hosted source. Existing Interakt intake and WhatsApp conversion settings remain independent.

The service receives signed Meta notifications and holds selected Page/form/lead identifiers. The customer site's scheduled worker polls those notifications, saves encrypted local work, acknowledges durable receipt and uses the existing importer. Delivery therefore depends on the site's scheduler and can take multiple worker runs. Bounded catch-up also uses the service. One Page can belong to only one provisioned installation in this initial service.

Customers require a public HTTPS return URL. Before publisher provisioning, Connect Facebook focuses a visible explanation of the service and public HTTPS prerequisites; the localhost HTTP development site is not a live OAuth qualification environment. Pending consent is bound to the initiating administrator's WordPress login session and expires after 15 minutes. Tokens, installation keys and pending claims are excluded from browser responses and portable backups.

## Manual Instant Form sync: four guided steps

Manual Facebook setup opens by default when the shared service is unavailable. Four expandable steps cover Page/forms, credentials, webhook, and check/enable. Continue buttons move between steps without discarding entries; Save progress submits the shared settings form. On reload, the first incomplete saved step opens. Hosted selections cannot be overwritten by general settings saves.

Credential fields stay blank after saving by design. The view receives boolean saved/managed metadata only, and both the badge and description report “Saved securely” when a secret exists. Blank submissions retain saved values; replacements show “Ready to save” until submitted. Server-managed credentials cannot be changed in the form.


Open **Settings → Lead capture → Direct Meta lead sync** in the CRM administrator or shared workspace settings.

1. Create/use the business-owned Meta app intended for lead retrieval. Confirm its access to the advertising Page and form leads. The existing CAPI token is a separate credential and is not assumed to have lead access.
2. Save the Page ID, app ID, one or more form IDs (maximum 20), lead-retrieval token, app secret and a chosen verification token. Credentials are write-only and encrypted, with optional `IDLM_META_LEAD_ACCESS_TOKEN`, `IDLM_META_LEAD_APP_SECRET` and `IDLM_META_LEAD_VERIFY_TOKEN` server constants. Blank fields retain saved values; clearing uses the explicit checkboxes.
3. Use Save progress with sync off while configuring the webhook. Enable direct sync in step 4 after checking the saved connection. If required values are missing, the settings form stays visible with a list of missing fields and the non-secret draft values. Credentials already saved remain stored. Leave direct sync unchecked to save an unfinished setup. Use a public HTTPS WordPress URL; the local development site alone cannot receive Meta notifications.
4. Webhook verification accepts a saved Page ID and verification token before sync is enabled; signed POST intake remains disabled until enablement. In the Meta app, configure the displayed `/wp-json/idlm/v1/meta-leads` callback and the same verification token for the **Page / leadgen** webhook. Subscribe the app to the configured Page's `leadgen` field as well. App-level subscription alone is insufficient. Check current access/review requirements for the business/app before production use.
5. Click **Check saved Meta lead connection**. This reads the Page subscription, the first form's Page ownership, and lead-read access. It does not create subscriptions, modify ads, or certify all remaining forms.
6. Use Meta's Lead Ads Testing Tool to submit a lead for each form. Verify the phone/email, custom questions, Page/form identity and normal CRM assignment. The test API's dummy webhook IDs cannot be fetched as real leads. Test with an actual generated test lead.
7. Keep Pabbly available until validation succeeds, then disable its CRM delivery. Both paths must preserve the original Meta ID in `fb_lead_id`; the generic webhook now also recognizes top-level `leadgen_id` for platform `meta`. Exact external ID plus existing email/phone policy prevent a second canonical lead. Pabbly mapping remains independent of direct field mappings.

Direct mapping consumes Meta's named `field_data` answers. Default contact fields are `first_name`, `last_name`, `email`, `phone_number`; `full_name` is a fallback. Map custom questions using their exact API field names. The connector fixes stage/source/Meta ID internally and never accepts a form answer as authority to qualify, assign or mark a lead Won.

Direct sync and the generic webhook use separate credentials and field mappings. They can run independently or overlap. When both identify the same Meta submission, the canonical lead and touchpoint remain shared: incoming attribution fills blank fields without replacing existing values, and the normal CAPI delivery receipt prevents a duplicate initial event. An attribution-write failure rolls back the whole inbound update so the webhook can retry. The separate webhook's configured UTMs remain literal values and are not derived from direct-sync campaign fields.

An inbound mapped submission time is recorded on the touchpoint, not as the lead's `conversion_time`: the lead column represents a current Won close. MySQL-format dates are preserved and ISO timestamps with offsets are converted to the site's timezone. Blank or invalid timestamps are stored as unknown, not zero dates; the rest of the webhook remains eligible for intake. This prevents new affected webhook leads from making portable backups invalid; existing historical zero dates are not automatically changed by this iteration.

The connector uses the lead, Page and form identifiers from a notification, then checks the returned lead/form IDs against them. Authenticated Graph retrieval requests the fields in Meta's Lead SDK model: `id`, `created_time`, `form_id`, `ad_id`, `ad_name`, `adset_id`, `adset_name`, `campaign_id`, `campaign_name`, `is_organic`, `platform`, `partner_name`, `field_data`, `custom_disclaimer_responses`, `home_listing`, `post`, `post_submission_check_result`, `retailer_item_id` and `vehicle`. Actual availability depends on Meta's API version, permissions and the lead; some may be absent or unavailable. If Meta rejects the full request, the connector tries a smaller ad-attribution set, then the original `id,created_time,form_id,ad_id,field_data` request so optional fields do not prevent ingestion. The separately deployed Facebook Connect service must also run the updated proxy before it can accept the expanded requests; an older service falls back to the original fields.

The returned requested fields, including all form answers and any disclaimer responses, are retained as an encrypted `meta_lead` snapshot within the lead's acquisition context. This is one current acquisition snapshot per CRM lead, not an immutable history of every submission; a later Instant Form acquisition can replace it. Submissions held for ambiguous identity review do not yet retain this full snapshot. The connector does not retain the complete webhook notification, fetch the separate form object's name or tracking parameters, retroactively enrich historical leads, or guarantee literal UTM values. UTMs may be present in custom answers when collected by the form, but campaign/ad-set names and IDs are not interchangeable with UTM source, medium, campaign, content or term. Original Meta IDs remain strings, including in CAPI JSON; no conversion to floating point occurs. Existing CRM CAPI events use the Meta lead ID and appropriately hashed customer identifiers; storing the broader response does not automatically send arbitrary lead fields or answers to CAPI.

## Interakt WhatsApp intake

Keep the existing Interakt number and signed `/wp-json/idlm/v1/interakt-webhook` URL. Enable **Create or match CRM leads from incoming Interakt messages** in Lead capture. This is independent of direct Instant Form sync. Interakt itself must remain enabled and have its webhook secret configured. Confirm that the Interakt subscription includes incoming customer messages; outbound delivery/campaign-status events never create leads.

With intake disabled, the prior behavior remains: messages attach to existing canonical leads only. With intake enabled, the authenticated `message_received` handler validates/normalizes contact and message identity and saves encrypted work before returning 200. The worker uses the normal inbound upsert, preserves existing owners/stages, records the activity and message receipt, and commits attribution with that lead transaction. Ambiguous contacts follow the existing identity-review flow. A held WhatsApp review does not yet replay its first message or bind advertising attribution automatically after a manager decision; review those manually.

The supported referral paths are `data.message.referral` and `data.message.meta_data.referral`. Accepted fields are `ctwa_clid`, `source_id` and `source_url`. Interakt's published generic message example does not guarantee these fields. Validate an actual Click-to-WhatsApp ad message before relying on campaign attribution. Callback data and arbitrary customer traits are not treated as Meta click IDs. Without explicit click evidence the source is **WhatsApp**, rather than **WhatsApp Ads**. No visitor IP, user agent, browser cookie or Meta Instant Form ID is invented.

## WhatsApp conversion reporting

Reporting is separately off by default. Configure the Facebook Page ID that ran the ads, confirm the original referral click ID is present, and enable **WhatsApp campaign conversion reporting**. The current Meta CAPI destination/token must be authorized for the intended business-messaging dataset. Do not double-report the same outcomes through both Interakt's conversion feature and this CRM.

WhatsApp conversions use `action_source=business_messaging`, `messaging_channel=whatsapp`, and `user_data.ctwa_clid/page_id`. Only Won → Purchase is enabled by default. Other outcomes require explicit stage mappings to event names supported by the configured business-messaging integration. Without required identifiers or opt-in no WhatsApp Meta request is sent. Ordinary follow-ups do not overwrite an existing Instant Form acquisition source. Original Instant Form events continue through the CRM CAPI mapping.

If a canonical lead has a stored Meta Instant Form lead ID, its Meta CAPI events use that ID and the normal CRM event path even if a WhatsApp referral was recorded before or after it. This precedence also lets a webhook-sourced Meta lead report without reading unrelated connector attribution. Leads without a Meta lead ID continue to require the WhatsApp opt-in and referral identifiers for business-messaging reporting. The webhook-supplied ID is trusted as configured; it is not independently validated with Meta by this decision.

CRM stage events no longer attach the salesperson/webhook/cron request IP or user agent, or a fabricated homepage event URL. A bare stored `fbclid` is no longer turned into a fabricated `_fbc` value using the CRM creation time; the click ID stays available for reporting, but CAPI matching does not currently receive `_fbc` or `_fbp`. Capturing authentic browser values and consent remains separate work.

## Reliability, retention and recovery

`IDLM_Lead_Connector` owns intake, retrieval, settings, attribution and recovery. Normal lifecycle mutations still use `IDLM_DB::upsert_inbound_lead()`; `connector_attribution`, `connector_message` and `connector_queued_at` are internal options used at the checked aggregate boundary. The WhatsApp inbox permits a nested call only when the connector explicitly requests the existing owned lead transaction.

- A minute worker runs through Action Scheduler when available, otherwise WP-Cron. Activation/runtime setup registers it and deactivation clears it. Scheduler arguments contain no contact data or credentials. Use a reliable production cron runner.
- Pending options `idlm_connector_job_{sha256(provider|event_id)}` contain encrypted, bounded payloads. Callback authentication and durable storage happen before acknowledgment. Reads of current configuration and credentials bypass stale option caches. Per-event database session locks prevent overlapping imports; crash recovery can safely repeat an upsert/message receipt.
- The sweep examines at most ten pending jobs per tick with a keyset cursor. Failed jobs retry five times with bounded exponential delays; Save settings can reset failed attempts among the first 100 pending records. The global last result contains only provider/state/time. No provider response, secret, message or contact is added to that status.
- Pending payloads expire after seven days when the worker next visits them. Minimal `idlm_connector_receipt_*` HMAC fingerprints/outcomes prevent a completed, expired or cancelled notification from silently becoming a new lead. These receipts are retained independently of diagnostic logs.
- Catch-up visits one configured form/page per tick, with 25 results per API page and a 15-minute pause after a completed scan. It starts at the Page's initial settings-save time, overlaps completed windows by one hour, keeps a fixed start watermark across pagination, and never intentionally retrieves more than seven days of outage history. It does not import historical leads before initial setup. A changed form list must be tested explicitly. Persistent errors retain the watermark and reset a failing cursor after three attempts. Only cursor values are reused; arbitrary provider `next` URLs are never fetched.
- `idlm_connector_attribution_{lead_id}` stores encrypted acquisition context, including the potentially sensitive raw Meta form answers and optional provider fields, independent of touchpoint-log retention. The requested provider snapshot is bounded at 512 KiB; a larger or unencodable snapshot fails intake rather than silently dropping fields. Lead deletion/reset removes it. HMAC identity tombstones prevent older queued input from recreating a deleted contact; a later new submission may create a new lead. Recovery-generation fencing cancels queued work from before reset/restore. Operators must account for the extra retained personal information in their privacy notices and retention practices.
- Connector runtime/attribution options are excluded from portable plugin backups. Same-site restore preserves local attribution and receipts; a new-site restore does not reconstruct this attribution. Use a full WordPress database backup where acquisition-context recovery is required. Credentials also remain outside portable exports.

Live provider acceptance, app permissions, real Interakt referral shape, scheduler delivery latency, and sustained high-volume behavior require staging/live qualification. Local tests mock all provider HTTP and mail; they are not proof of a configured production connection.
