# CORE-008 — identity-review lifecycle and erasure

Author / Builder: **Shashi**. Date: **2026-10-07**. Candidate **1.102.54**, core schema **1.3.9**; quotation **2.5.0** and routing **1.0.1** unchanged. Status: **IMPLEMENTED locally, not CLOSED**.

## Finding and implemented policy

The immutable [CORE-008 finding](audit-2026-10-06/CORE-REVIEW.md#core-008--p2-medium-crm-reset-leaves-pending-identity-review-pii-and-there-is-no-resolution-interface) identified retained email/phone/candidate PII after reset and the absence of any resolution interface. The bounded Graphify query “Inbound identity review resolution deletion reset retention transaction” connected the lifecycle, deletion/reset and recovery boundaries. Current source verified the omission and the existing checked transaction/identity-lock owners before implementation.

**Identity reviews** is a native WordPress administrator utility available to an enabled, effectively enrolled assignment manager (`manage_options` or `idlm_assign_leads` with CRM access). Broader read visibility alone does not authorize inspection or resolution. The page lists 25 rows by increasing ID with status filters and candidate contact details, escaped output and labeled native form controls. Resolved decisions are read-only. The dedicated POST action requires a user/review/recovery-generation-bound WordPress nonce, a known decision and a nonempty reason of at most 1000 bytes. SQL failures, stale rows, unavailable/duplicate/foreign candidates and revoked managers fail without acknowledging success. Manager account/meta/role grants are refreshed from locking reads after the review lock wait.

- **Use canonical candidate (`matched`):** choose a live, nonduplicate ID from the held candidate list. Fill only empty supported fields and preserve existing contacts, workflow and ownership; record one attribution touchpoint and an identity-review activity. Attribution hook/cache intent uses the existing durable after-commit outbox.
- **Create separate (`separate`):** explicitly bypass duplicate detection through the canonical insert service. Create a New, unassigned lead from the supported sanitized contact/project/attribution fields, one touchpoint and audit activity. Submitted ownership, stage, commercial state, files and credentials cannot set the new lead's state. Normal assignment remains a subsequent CRM operation; resolution does not route or create a pre-sales plan.
- **Reject (`rejected`):** persist the actor, timestamp and required reason on the review without creating a lead, task or delivery intent. Webhook replays report the rejection rather than claiming pending human review.

Decisions are terminal. Intake and resolution share deterministic identity locks; the review row is locked and its immutable input is rechecked before mutation. All required writes and commit use `IDLM_Lead_Transaction`; an error rolls back the aggregate. Concurrent decisions can commit only one result. A form obtained before reset/restore is invalid in the new recovery generation.

## Storage, replay and recovery

Add nullable `submission_data`, `external_id`, `resolved_lead_id`, `resolved_by`, `resolved_at` and `resolution_note`, plus the unique nullable `(platform, external_id)` key and resolved-lead index. The existing verified installer controls the independent schema marker. The stored submission is an allowlist of supported contact/project/attribution fields; diagnostic payload redaction remains in place.

An external-ID replay first consults the durable review, including terminal decisions, and returns its result without another lead, touchpoint, activity or routing. Submissions without an external ID remain independent submissions. Replay evidence lasts only as long as the retained review; erasure/retention removes it. This does not promise permanent provider replay protection after erasure or expiration (broader minimal replay evidence remains CORE-012/provider work).

Legacy pending rows preserve known email, phone, source, candidate hints and redacted diagnostic evidence. Missing names/project values or external IDs cannot be reconstructed; separate creation uses only known data and can be completed later through normal lead editing. No historical identity decision is invented. Complete old backup inventories (core 1.3.5–1.3.8, including versionless inventories) receive only the nullable additions before normal validation; current incomplete inventories still fail before deletion. Terminal decisions round-trip with exact metadata and validated live target references. Legacy candidate IDs remain historical hints and may already be dangling. Restoring an older backup can intentionally recover old PII, as with other CRM data.

## Erasure and retention

Reset now explicitly deletes `idlm_inbound_submission_reviews` in its existing InnoDB transaction/fence, with an independent regression that names the table rather than copying the reset manifest.

Lead deletion/bulk deletion erases the **whole review row** when any candidate ID, resolved lead ID or normalized email/phone associates it with an erased lead. This includes pending and terminal decisions, stored submission, diagnostic payload and reason. Ambiguous reviews involving another retained candidate are also erased; preserving that held copy would preserve the erased person's PII. Malformed legacy candidate JSON is conservatively erased. Unrelated valid reviews remain. Reads and deletes are checked under the deletion transaction; failure rolls back lead and review changes. Deletion participates in the existing recovery fence and requires the review table to be InnoDB. The scan reads 100 rows at a time; total deletion time at large volume remains a CORE-012 qualification gate.

Review retention keeps the existing `touchpoints_days` policy (default 90 days from receipt) for all statuses. One checked transaction deletes at most 100 expired rows. A full batch or failure schedules a one-minute continuation; retries use the same expiry predicate without a cursor that could skip failed rows. Row locks serialize overlapping deletes. The function returns an error on persistence failure. Deactivation clears the continuation hook and preserves data. The full backup includes review PII; private files, users and delivery jobs retain their separately documented recovery policies.
