## Retention policy and recovery

`IDLM_Data_Retention::init()` registers/schedules work without synchronous purges or completion markers. Each invocation enters the recovery fence, acquires a database-session retention lock without waiting, and performs at most one checked 100-row batch. It rotates fairly through touchpoints, all identity-review states, CAPI logs, audience logs, telemetry, diagnostic activities, and legacy audience payload compaction. A busy/error/full backlog schedules a one-minute continuation using Action Scheduler when available, WP-Cron otherwise. Deactivation clears both continuation backends and the daily hook.

The configured touchpoint/integration/telemetry lifetimes remain 90/180/14 days by default, with a minimum one day. Diagnostic activity types `audience_sync`, `capi_sync`, `capi_queue`, `capi_abort` retain seven-day detail. CAPI rows use integration retention; the former unconditional seven-day CAPI delete is removed. Independent durable provider-delivery claims and replay beyond configured expiry remain **INT-008** work; this slice does not claim that configured log expiry is an adequate replay-claim lifetime.

`idlm_retention_progress` is a non-autoloaded, protected runtime option containing recovery generation, cutoff, next stage, stage backlog flags, processed count, completion, last update, and a generic error code. Batch writes and progress commit together after checking transactional engines and session ownership. Retrying deletes the first remaining expired rows, so a killed process or failed checkpoint cannot advance past unremoved PII. Recovery-generation changes restart the sweep. Restore neither imports nor exports this checkpoint.

Failures preserve the committed position and record `batch_failed` when the database can persist it. The operational-health retention check becomes critical even if the recurring hook is scheduled. Database unavailability may prevent persistence of the fault itself; callers receive failure and continuation remains eligible. No SQL, contacts or payloads enter progress. Compaction stops between updates after a five-second application deadline, and fetches only ID, byte count and SQL SHA-256 for up to 100 large bodies; it stores a small content-free summary. It cannot allocate an entire oversized historical payload in PHP.

## Read and download contracts

- **Task queue:** default attention and completed history return at most 50 cards, with additive `has_more`/`next_cursor`. Qualification slots collapse to one card per lead in SQL before pagination. Existing pending/Lost, upcoming-eight-day, undated-manual, historical pre-sales and live lead-access rules remain. SQL computes full scoped attention totals, independent of page size. `counts_only=1` returns totals without customer cards or qualification-history work.
- **Task cursors:** existing signed cursor machinery binds user, view, effective SQL scope, local day and recovery generation. Invalid, cross-user/view/scope or obsolete recovery cursors deny. Pages are live views: changes to due dates, task status or ownership can move/remove work; refresh starts a new traversal. There is no immutable task snapshot.
- **Qualification summaries:** the queue uses 100-date history pages, carrying the existing calendar-day calculation across page boundaries, retaining only six completed cycles and active progress. The response shares a five-second application deadline for these reads and returns a retryable error rather than fabricated progress on failure. Other domain callers retain the established compliance contract.
- **WhatsApp:** counts aggregate in SQL; list/export filters use correlated `EXISTS` with sanitized per-lead read positions. No PHP activity-history scan or growing activity-ID list is needed. Authorization is evaluated on each read without the former permission-stale unread cache. Legacy prefixed comments and typed replies remain supported. Compatibility ID helpers now accept `after`/`limit` and return at most 100 ascending lead IDs; internal callers use predicates, so this cap does not truncate list/export matches.
- **Lead CSV:** preserve administrator/nonce checks, filters, descending ID order, 40 columns and text-cell formula safety. Read explicit export columns in 100-row ID keysets and stage a temporary file before attachment headers. Limits: **10,000 leads, 32 MiB, 20 seconds of application work**. Oversize/read/write/deadline failures return an explanatory error without a successful-looking partial download. Narrow filters or selected IDs to fit the limit. New higher IDs after the first page are excluded; mutable field values remain live between reads. The temporary file is closed on success/failure and automatically removed; this is not a durable asynchronous export job.

Row/allocation limits do not impose a hard server-side SQL execution deadline or eliminate SQL scans/sorts. A blocked database statement can exceed the application budget before control returns. Host lock/query timeouts and production workload qualification remain necessary; no hard end-to-end SLA is asserted.
