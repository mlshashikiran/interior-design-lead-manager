## Policy and behavior

- Manual work is a snapshot of selected lead IDs and current enabled rule definitions. It never scans unrelated matching contacts. A legacy ID-only queue is adopted in batches. Duplicate/stage/call/quality exclusions and usable platform identifiers apply at the claim boundary, using current primary lead rows; queued IDs cannot override them. Google selection uses the same rule predicate as its authenticated pull feed.
- Disabled/changed rules and missing credentials retain unresolved manual work. Explicit reselection binds current saved definitions and retries confirmed failures, retaining already accepted destinations for an existing selection. Queue removal stops selected manual work and keeps unknown delivery fences. It does not remove customers from a provider audience or disable ordinary scheduled selection.
- Nonautoload `idlm_audience_work_<lead_id>` records contain version, recovery generation, numeric lead ID, rule fingerprints, destination fingerprint, manual targets and status/attempt/cooldown/UTC-day state. They contain no contact data, credential, request/response or commercial payload. Rules bind platform/target/filter/value configuration; uncertainty fences bind platform/target so changing a filter cannot reopen the same unknown destination. Malformed state and unsupported engines fail closed.
- One database session lock serializes enqueue/cancel/manual/scheduled dispatch. Each selected page commits processing state in an independent checked InnoDB transaction before HTTP. Provider audit insertion must return a positive log ID; audit and all page outcome acknowledgements commit together. A write/commit failure leaves processing evidence that becomes uncertain on the next attempt. No HTTP runs inside that transaction.
- Confirmed temporary rejection (429, 5xx or a transient error flag) retries at most three times, with 60-second minimum cooldown and bounded Retry-After handling (numeric seconds or HTTP date, capped at one hour). Permanent rejection retains blocked work until explicit reselection/removal. Transport errors, malformed/unexpected acceptance, interrupted processing and recognized partial-page failure hints remain uncertain and are never automatically resent. Partial destination success keeps successful destinations acknowledged while retrying the failed destination. Page acceptance is adapter-level acknowledgement, not proof that every identifier matched a customer.
- Google work reports **mapped**, separately from provider-accepted uploads. It records the current pull mapping without claiming Google fetched the feed.
- Manual adoption and contact pages use at most 100 IDs; each invocation sends at most three pages and checks a 35-second application deadline between pages. Existing 30-second transport timeout remains, so an in-flight call can extend the between-page deadline. Scheduled selection uses primary keyset cursors and checked daily scan state; already accepted contacts skip replay within the UTC-day window. Failed scheduled pages retain their cursor and receipts, and continuation callbacks carry generation/mode/day only. Pending selected IDs stay outside the concurrent ordinary scheduled scan. A primary queue reread preserves newly enqueued IDs; unfinished pages rotate to avoid a blocked head starving later selections.
- Queue state is excluded from JSON backup. Same-site restore/reset clears audience work/scan/queue and cancels continuation hooks; stale generations/days cannot dispatch. Explicit lead erasure removes its work record and queue ID transactionally. Restore starts a new audience delivery epoch; it does not preserve previous uncertainty across that recovery. Customer removal/consent and provider reconciliation are not implemented by queue cancellation.
